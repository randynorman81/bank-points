1. Intro to Programming with Karel

Karel
A robot dog that lives in a grid world of streets (rows) and avenues (columns). Karel does exactly what you tell it, in the exact order, and nothing else.
Program
A list of instructions (commands) that the computer runs in order, top to bottom.
Ball
The small object Karel can drop or pick up on a corner (sometimes called a beeper).
CommandWhat it does
move();Moves Karel forward one square in the direction it's facing.
turnLeft();Turns Karel 90° to the left without moving.
putBall();Drops one ball on Karel's current corner.
takeBall();Picks up one ball from Karel's current corner.

Every command ends with a semicolon ;, which marks where one instruction ends. Every command also has parentheses (). Command names are case-sensitive: turnLeft is right; turnleft and TurnLeft are errors.

Order matters. move(); turnLeft(); move(); and turnLeft(); move(); move(); use the same commands but put Karel in different places.

2. More Basic Karel

Reading the world first: before writing code, find where Karel starts, which way it faces (the triangle points that way), where the walls are, and where the balls are. Trace the path with your finger and count the moves and turns.

move(); move(); turnLeft(); move(); putBall(); turnLeft(); turnLeft(); // two lefts = turned all the way around (180°) move();
Crashes: move(); into a wall, or takeBall(); on a corner with no ball, stops the program with an error. Karel doesn't remember anything on its own; it only knows what your commands tell it.

3. Karel Can't Turn Right

Karel only knows turnLeft();. There is no built-in turnRight(); in regular Karel.

4. Functions in Karel (+ the Main Function)

Function
A named group of commands you define once and can run (call) as many times as you want by using its name.
Defining vs. calling
Defining writes the function: function turnRight() { ... }. Calling runs it: turnRight();
main()
The special function where every program starts. Karel only runs code that is inside main() or inside a function that main() calls.
// DEFINE a new command function turnRight() { turnLeft(); turnLeft(); turnLeft(); } // the program STARTS here function main() { move(); turnRight(); // CALL it move(); }
  • Everything inside the curly braces { } belongs to the function. Every { needs a matching }.
  • Names use camelCase: no spaces, first word lowercase, each new word capitalized (turnRight, buildTower).
  • Why use functions: less typing, fewer mistakes (fix it in one place), and easier to read.
Common mistakes: calling without parentheses (turnRight;), commands written outside of any function, and a missing closing }.

5. Top Down Design and Decomposition

Decomposition
Breaking a big problem into smaller, simpler sub-problems.
Top down design
Starting with the big goal and working down into smaller pieces, one layer at a time, before writing code. Each piece usually becomes its own function.
function buildTower() { putBall(); putBall(); putBall(); } function moveToNextSpot() { move(); move(); } function main() { // reads like the plan: build, move, build buildTower(); moveToNextSpot(); buildTower(); }

The 4 planning steps: (1) say the big goal in one sentence, (2) list the major steps in plain English, (3) turn each step into a function, (4) call them in order inside main(). Give functions clear names (buildTower, not doStuff).

6. Commenting Your Code

Comment
A note in the code for humans. The computer ignores it completely; it has no effect on what Karel does.
// A comment starts with two slashes and goes to the end of the line move(); // it can also go at the end of a line of code /* A multi-line comment starts with slash-star and ends with star-slash */

Good comments explain why or what a section/function is for (like one line above each function). Poor comments just repeat the obvious (// move forward above move();).

7. Abstraction

Abstraction
Hiding the complicated details behind a simple name, so you can use something without thinking about how it works inside.

When you call turnRight();, you don't think about the three turnLeft(); calls inside it. The details are still there and still run; they're just hidden, not deleted. Real-life examples: a car's gas pedal, a TV remote's power button, ordering "one burger" at a counter.

Connection: top down design uses abstraction. main() is written with function names like buildTower(), hiding the detailed commands one layer below.

8. Super Karel

Super Karel is the same robot with extra built-in commands, so you don't have to write them yourself:

CommandRegular KarelSuper Karel
move(); turnLeft(); putBall(); takeBall();Built inBuilt in
turnRight();You must write itBuilt in
turnAround();You must write itBuilt in

Super Karel doesn't add every command you might want. For anything else, you still write your own function. And turnRight() is still abstraction: it still does the work of three left turns underneath.

9. For Loops

For loop
Repeats a block of code a fixed (known) number of times.
Iteration
One trip through the loop's body.
for (var i = 0; i < 4; i++) { move(); putBall(); } // runs 4 times: i = 0, 1, 2, 3 (move, putBall) x 4
PartMeaning
var i = 0Start the counter at 0.
i < 4Keep looping while this is true. The number here is how many times it runs.
i++Add 1 to i after each iteration.

The three parts are separated by semicolons, not commas. Everything inside the braces repeats each time, as a group. A loop can call your own functions too.

Off-by-one: i <= 4 starting from 0 runs 5 times, not 4. A loop doesn't check for walls: if 5 moves would hit a wall, the loop crashes Karel.

10. If Statements and Conditionals

Condition
A yes/no question whose answer is true or false. Asking a condition does not move Karel.
If statement
Runs its block only when the condition is true. If it's false, the block is skipped and the program continues after it.
ConditionTrue when...
frontIsClear() / frontIsBlocked()no wall in front / a wall in front
leftIsClear() / rightIsClear()no wall to Karel's left / right
ballsPresent() / noBallsPresent()there is a ball on this corner / there is no ball
facingNorth(), facingEast(), ...Karel faces that direction
if (frontIsClear()) { move(); // only runs when there's no wall ahead }
The condition goes inside parentheses: if (frontIsClear()). frontIsClear() and frontIsBlocked() are opposites: mixing them up flips your logic.

11. If/Else Statements

An else block runs when the if's condition is false. Exactly one of the two blocks runs every time: never both, never neither.

if (ballsPresent()) { takeBall(); } else { putBall(); // runs only when there is NO ball }
  • else never has its own condition: it's just else {.
  • else must come right after the if block's closing }.
  • If you want two checks that could both run, use two separate if statements instead.

12. While Loops

While loop
Repeats as long as a condition stays true. Use it when you don't know how many times in advance.
Infinite loop
A loop whose condition never becomes false, so it never stops.
while (frontIsClear()) { move(); // walks until it reaches a wall, however far that is }
For loopWhile loop
Use whenYou know the exact number of repeatsYou repeat until something happens
Stops whenThe counter reaches its limitThe condition becomes false
Example"Move 4 times""Move until you hit a wall"
Infinite loop: something inside the loop must eventually make the condition false. while (frontIsClear()) { turnLeft(); } never moves Karel, so if the front starts clear it spins forever.

13. Debugging Strategies

Bug
When the program does something different from what you wanted.
Debugging
The process of finding and fixing bugs.
  1. Say what should happen (be specific).
  2. Say what actually happens.
  3. Find the exact line where they stop matching.
  4. Change one thing, then run it again.
Kind of bugWhat you see
Crash (error)The program stops, often with a message and a line number (hit a wall, took a ball that wasn't there, missing brace).
Wrong result (logic bug)The program finishes, but Karel ends in the wrong place or the balls are wrong. Nothing tells you where; you trace the logic.

Techniques: trace the code on paper first, test one function at a time, check braces/parentheses/semicolons, and re-read the world (walls, starting direction). Randomly changing code until it works is not debugging.
