Top Down Design and Decomposition

Before you write a single line of code for a big task, break it into smaller pieces first. This is how real programmers plan — and it's how you'll build big Karel programs without getting lost.

00

Two Big Words, One Simple Idea

Decomposition means breaking a big task into smaller sub-tasks. Top down design is the process of starting with the big goal and working your way down into those smaller pieces, one layer at a time, before writing any code.

A non-Karel example: "clean my room" is really "make the bed" + "put away clothes" + "throw away trash" + "organize the desk." You didn't think of all four steps at once — you broke the big vague task down into smaller, doable ones.
01

Decomposing a Karel Task

Say the goal is: "build a tower of 4 balls on this corner." Instead of writing 4 separate putBall(); lines and hoping you remember to stack them right, break the goal into a function first.

function buildTower() { putBall(); putBall(); putBall(); putBall(); } function main() { buildTower(); }

Now main() reads almost like plain English: "build a tower." All the messy detail of exactly how is tucked inside buildTower().

A bigger example: build 3 towers in a row

function buildTower() { putBall(); putBall(); putBall(); putBall(); } function moveToNextSpot() { move(); move(); } function main() { buildTower(); moveToNextSpot(); buildTower(); moveToNextSpot(); buildTower(); }

main() now reads as a short list of big steps — build, move, build, move, build — instead of a long, hard-to-follow list of every single move(); and putBall();.

02

How to Actually Plan This Way

Step 1

Say the big goal in one sentence

"Build 3 towers in a row." Don't think about commands yet.

Step 2

List the major steps

Build a tower. Move to the next spot. Repeat. Still no commands — just plain English steps.

Step 3

Turn each step into a function

Now write buildTower() and moveToNextSpot() as their own small functions.

Step 4

Call them in order inside main()

Put the big-picture plan together using the function names you already wrote.

03

Common Mistakes

Mistake 1

Writing all the commands first, planning never

Jumping straight to typing move(); and putBall(); over and over almost always leads to a confusing mess. Plan the big steps first.

Mistake 2

Functions with unclear names

A function named doStuff() tells you nothing. buildTower() tells you exactly what it does — name your functions like a sentence.

Mistake 3

One giant function that does everything

If a function is doing five unrelated things, it's a sign you haven't broken the problem down far enough yet.

Plan the big steps first. Turn each one into a function. Then call them in order.
