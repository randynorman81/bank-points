Debugging Strategies

A bug is when your program does something different than what you wanted. Debugging isn't luck or guessing — it's a repeatable process anyone can follow.

00

The Debugging Process

When something goes wrong, resist the urge to change five things at once and hope. Follow these steps in order instead.

Step 1

Say what SHOULD happen

Be specific. "Karel should end up facing north, at the corner with the ball" — not just "it should work."

Step 2

Say what ACTUALLY happens

Run the program and watch closely. Where exactly does it stop matching what you expected?

Step 3

Find the exact line

Compare your plan to your code, line by line, starting from wherever things first went wrong.

Step 4

Change ONE thing

Fix your best guess, then run it again. If you change three things at once, you won't know which one actually fixed it.

The #1 mistake beginners make: randomly changing code and re-running it, hoping something works, without ever figuring out why it was broken. This might accidentally fix one bug while creating a new one you don't notice yet.
01

Two Kinds of Bugs

Crashes

Karel runs into a wall, or tries to takeBall(); with none there. The program stops and usually tells you which line caused it — read that message, it's telling you exactly where to look.

Wrong result, no crash

The program finishes, but Karel ends up in the wrong place, or the balls are in the wrong pattern. These are harder — nothing tells you where the problem is, so you have to trace through your own logic.

02

Techniques That Actually Help

Technique

Run it one function at a time

If main() calls several functions, comment one out (or temporarily remove the call) and test the rest. Narrow down which function has the actual bug.

Technique

Trace it on paper first

Before you even run it, walk through your code by hand, line by line, predicting what Karel does at each step. Compare that prediction to what actually happens.

Technique

Check your braces and parentheses

A huge number of bugs are just a missing {, }, or ; somewhere. Count them before assuming your logic itself is wrong.

Technique

Re-read the world before you code

A lot of "bugs" are actually a misread map — miscounting a wall's position or which way Karel starts facing. Double check the picture first.

Say what should happen, say what does happen, find the exact line, change one thing at a time.
