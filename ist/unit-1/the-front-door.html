The Front Door

Every website you trust is a building with strangers walking up to the door all day. HTTPS, CAPTCHA, 2FA and OWASP are the four things standing between them and what's inside.

01 / TRANSIT

HTTPS

The lock on the connection itself — scrambles what you send so no one on the way can read it.

02 / ENTRY

CAPTCHA

The doorman — checks that whoever's knocking is a person, not a script.

03 / IDENTITY

2FA

The second deadbolt — a stolen key alone isn't enough to get in.

04 / INSPECTION

OWASP

The building code — the catalog of ways buildings like this one usually fail.

01

HTTPS — the lock on the connection

Plain HTTP sends everything — your password, your messages, your search — as plain, readable text. Anyone else on the same network can read it as it passes by.

What the padlock icon actually checks

Encryption
Data is scrambled (via TLS) so it's unreadable to anyone intercepting it in transit — including on public Wi-Fi.
Certificate identity
Confirms you're actually talking to the domain in the address bar, not an imposter server pretending to be it.

Redline: the padlock is not a trust badge

HTTPS proves your connection to a site can't be read by a stranger in the middle. It says nothing about whether the site itself is honest. A perfect copy of your bank's login page, built by a scammer at a look-alike domain, can carry a valid padlock too.

02

CAPTCHA — the doorman

CAPTCHA is actually an acronym: Completely Automated Public Turing test to tell Computers and Humans Apart. Its entire job is to slow down software pretending to be a person.

What bots do at a scale humans can't

Credential stuffing
Trying millions of leaked username/password pairs against a login page in minutes.
Ticket & sneaker bots
Buying out an entire concert or shoe drop in the first second, before a real person can click.
Spam & fake reviews
Flooding comment sections and review pages faster than any moderator could keep up.

It's evolved fast: distorted letters → "click every image with a crosswalk" → today's one-click "I'm not a robot" checkbox, which is quietly scoring your mouse movement and click timing in the background — the visible checkbox is almost a formality.

03

2FA — the second deadbolt

Security researchers group every way of proving identity into three "factors." Two-Factor Authentication just means combining two of them, so a leaked password alone isn't enough.

Something you know

Password / PIN

The weakest factor alone — it can be guessed, leaked, or phished.

Something you have

Phone / security key

A physical object an attacker would also need to steal.

Something you are

Fingerprint / face

Biometric — tied to your body, not memorized or carried.

Not all second factors are equal:

1
SMS text code

Vulnerable to SIM-swapping — an attacker convinces your carrier to move your number to their phone.

Weakest
2
Authenticator app

Generates a rotating code on your device itself — nothing to intercept over the phone network.

Better
3
Hardware security key

A physical key (like a YubiKey) that must be plugged in or tapped — virtually unphishable.

Strongest
04

OWASP — the building code

The Open Web Application Security Project is a nonprofit that studies how real websites get broken into, then publishes the patterns so builders can design around them — before an attacker finds them first.

Its best-known product is the OWASP Top 10 — a regularly updated list of the most critical risks to web applications. Two worth knowing by name:

#1
Broken access control

The most common flaw on the list — a user can view or edit data they were never supposed to reach, often just by changing a number in a web address.

#3
Injection

A form doesn't check what you type before running it — so instead of a name, you type a command, and the system obeys it.

OWASP isn't a company or a government body — it's the checklist real engineering teams actually build against before they ship.

05

Inspect the building

Six situations. Before you read the finding, decide for yourself which of the four locks is missing, working, or being tested.

Site A

A shopping site's address bar shows http://, not https://, and it's asking for a credit card number.

FindingNo HTTPS — the card number would travel unencrypted, readable by anyone on the same network.
Site B

A login page lets a script attempt ten thousand password guesses in one second with no slowdown.

FindingNo bot protection — a CAPTCHA or rate limit would have stopped this outright.
Site C

Someone's password leaks in a breach, but the attacker still can't log in — the account also asks for a code from their phone.

Finding2FA working as designed — the leaked factor alone wasn't enough.
Site D

A search box lets visitors type raw commands, and the server just runs whatever it's given.

FindingExactly the kind of flaw OWASP catalogs — an injection vulnerability.
Site E

Someone gets a text asking them to "confirm" a 2FA code for a login they never attempted.

FindingA live attack in progress — someone already has the password and is trying to get past the second lock.
Site F

The address bar shows a padlock and https:// — but the domain is a near-perfect misspelling of a real bank.

FindingHTTPS present, site still fake — the padlock never promised the site was legitimate.
Four locks, four different jobs. None of them cover for the other three — a building can pass three inspections and still fail on the fourth.

Try this

  • Check the lock. Visit any site you use daily and click the padlock icon in the address bar. Read what it actually claims to verify.
  • Time a CAPTCHA. Notice how much less you're asked to click than you were a few years ago. What changed?
  • Look up your 2FA. Check one account's security settings — is your second factor SMS, an app, or a key?

Talk about it

  • If a fake site can get a valid HTTPS padlock, what's actually stopping scammers from using one?
  • Why do you think broken access control — changing a number in a URL — is the single most common flaw on OWASP's list?
  • Is it worth losing a few seconds to a CAPTCHA on every site, if it stops bots on all of them?
  • Why would a company choose to publish its own security weaknesses publicly, the way OWASP catalogs them?

None of these locks were built to stop a person. They were built to stop everything else.

HTTPS, CAPTCHA, 2FA and OWASP all exist because the internet is full of things that aren't people — scripts, bots, and scanners moving at a scale no lock on a physical door ever had to handle. Knowing what each one actually checks is how you tell a locked door from a safe one.
