2.3 — Your First Sketch: Blink

🔔 Bell Ringer — Think About It
  1. Every Arduino sketch runs setup() exactly once and then loop() forever after — there's no way to make setup() run twice without restarting the board. Why do you think Arduino was designed with that permanent split instead of letting any code run "once" whenever you want?
  2. If you deleted the delay() from your Blink code entirely, the LED would technically still be blinking, just too fast for your eyes to see. Does something still count as "blinking" if a human can't perceive it?
  3. Most first-time bugs in this lesson aren't really about electronics — they're a wrong board selected, a missing semicolon, or a backwards LED. Why do you think tiny, "dumb" mistakes like these are often harder to find than big conceptual ones?
  4. delay() pauses your entire program while it counts down — nothing else can happen. Can you think of a project where that would be a serious problem, not just an inconvenience?

Notes

Look up these definitions:

  • Sketch
  • setup()
  • loop()
  • digitalWrite()

Key idea: every Arduino sketch has exactly two required functions — setup() runs once when the board powers on (use it to configure pins with pinMode()), and loop() runs forever after that. digitalWrite(pin, HIGH) turns a pin on (5V); digitalWrite(pin, LOW) turns it off (0V). delay(1000) pauses the program for 1000 milliseconds — without it, the blink would happen too fast to see. Common first-upload problems: wrong board or port selected in the IDE, missing semicolons/unmatched braces, or an LED wired backwards.

Why the wiring changed from 2.2: your LED there was wired straight to the 5V and GND pins — always on, no code involved. Today it's wired to a digital pin and GND instead, and it still works because a digital pin isn't just for reading input — set to OUTPUT with pinMode() and driven HIGH, that pin becomes its own tiny 5V source, exactly like the 5V pin, except your code controls it. digitalWrite(pin, LOW) drops that same pin to 0V, just like GND. That's the actual trick behind Blink: the pin itself is doing the powering, switched on a schedule your code controls, instead of a fixed always-on connection.
