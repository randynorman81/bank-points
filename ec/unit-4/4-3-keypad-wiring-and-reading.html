4.3 — Keypad: Wiring and Reading

🔔 Bell Ringer — Think About It
  1. A 4x4 keypad only needs 8 wires instead of 16, because it cleverly reuses rows and columns. Is there a way that cleverness could get the keypad confused, that a simpler but bulkier design wouldn't have?
  2. Debounce filters out the extra, unintended signals a single button press can accidentally create in its first few milliseconds. If an ATM keypad wasn't debounced, what might actually happen when someone tries to type their PIN?
  3. Each key press becomes one char, and a char array accumulates them into a sequence. Why does storing input as a growing sequence, rather than just the most recent key, matter for something like a PIN entry system?
  4. You're asked to test rapid presses today, on purpose, to look for debounce issues. Why is deliberately stress-testing your own input device with fast, messy real-world use more valuable than just testing it slowly and carefully once?

Directions

  1. Wire the keypad and install the keypad library.
  2. Print each key press to Serial Monitor and confirm all keys register.
  3. Build a char array logger storing each press.
  4. Test rapid presses for debounce issues.
  5. Submit your code and a photo.

Notes

Look up these definitions:

  • Matrix keypad
  • Row/column scanning
  • Debounce
  • char array

Key idea: a 4x4 keypad's 16 keys sit at row/column intersections — one wire per row (4) + one per column (4) = 8 wires total, instead of 16 individual pins the Uno doesn't even have. Pressing a key connects its row to its column; the code scans each combination to find which key is down. A keypad library packages this scanning so you just call it. Each key press returns a single char (e.g. '5'); a char array accumulates several presses in sequence — direct prep for 4.4's PIN logic. Debounce filters the rapid, unintended multiple signals a mechanical key produces in its first few milliseconds — without it, one press can register as several.
