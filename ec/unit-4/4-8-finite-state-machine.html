4.8 — Finite State Machine: Surface Level

🔔 Bell Ringer — Think About It
  1. Today's notes reveal that your PIN entry system from 4.4/4.6 was already a finite state machine — you just didn't have the vocabulary for it yet. Does giving something a formal name change how you think about it, even though the thing itself hasn't changed at all?
  2. A finite state machine is always in exactly one state — never zero, never more than one. Can you think of a real system, like a traffic light or a video game character, where being in two states at once would actually be dangerous or broken?
  3. You're told to diagram a system of your own choosing today, with nothing ambiguous or missing. Why might "nothing ambiguous" be the hardest part of that assignment — what tends to get left vague when people describe how something works?
  4. If a real system could get stuck in a state with no valid transition out of it, what would that actually look like to a user, and can you think of an app or device that's ever done that to you?

Directions

Discussion and diagramming, no hardware today. Bring up your 4.4/4.6 code for reference — you already built one of these.

Notes

Look up these definitions:

  • Finite state machine (FSM)
  • State
  • Transition

Key idea: a finite state machine has a fixed, defined set of possible states — the system is in exactly one at any moment, never zero, never more than one. Transitions are the rules/events that move it from one state to another. Traffic light: states red/yellow/green, transitions on a timer. Vending machine: waiting for payment, payment received, dispensing, out of stock. The reveal: your PIN entry system from 4.4/4.6 is already an FSM — states like "waiting for input," "checking PIN," "access granted," "access denied," with transitions like "4th digit entered" or "correct match." You built this without naming it — today gives you the vocabulary.
