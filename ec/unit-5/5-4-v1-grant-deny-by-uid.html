5.4 — V1: Grant/Deny by UID

Two-period lesson, first version of this unit's V1→V2→V3 sprint. You're knowingly building the exact vulnerability from 5.2 — a deliberate starting point, not a mistake.

Intro

Ask AI these questions; look over the answers.

  1. How would a program compare a scanned RFID card's UID against a stored list of authorized UIDs to decide whether to grant access?
  2. Explain to a middle schooler why a "whitelist" approach (only specifically listed items are allowed) might be safer than a "blacklist" approach (everything is allowed except specifically listed items) for something like building access.
  3. Create a simple flowchart showing the decision process: scan card, read UID, compare to whitelist, grant or deny.
  4. Why might storing authorized UIDs directly in code be a limitation for a real, large-scale access control system, even though it's fine for a small classroom project?
  5. Connect today's whitelist logic to something you already built earlier this course that also compared a value against a stored correct answer.
  6. Real access control systems sometimes log every entry attempt, not just grant or deny it. Why might that logging be valuable, even when access is correctly granted?

Notes

Look up these definitions:

  • Whitelist
  • Blacklist
  • Byte comparison
  • Access log

Key idea: a whitelist only allows specifically listed items (everything else denied by default) — the more secure default approach, and what V1 uses. A UID is made of several bytes, so comparing means checking every byte matches (same idea as Lesson 4.4's String comparison, different data type). V1's scope is intentionally limited — no servo yet (V2), no LCD yet (V3) — and it carries the exact vulnerability from 5.2: a cloned card with a matching UID gets in, with no way for V1 to tell the difference. That's a deliberate starting point to improve from.

Assignments

  • 5.4 — V1: Grant/Deny by UID. Wire a single LED as an access indicator. Scan one card and hardcode its UID as an authorized whitelist entry. Write byte-by-byte comparison logic, lighting the LED only on a full match. Expand your whitelist to support at least 2 authorized UIDs, and test thoroughly: both authorized cards plus an unauthorized one. Submit your annotated code and a photo of your working setup.
