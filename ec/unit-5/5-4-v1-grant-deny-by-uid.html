5.4 — V1: Grant/Deny by UID

🔔 Bell Ringer — Think About It
  1. You're about to build the exact same UID-only vulnerability you studied in the hotel keycard case, on purpose. Does knowingly building something insecure feel different than accidentally building it? Should it?
  2. A whitelist denies everything by default unless it's specifically approved. Can you think of a real system in your life that works the opposite way, allowing everything unless specifically blocked? Which approach seems safer, and why doesn't everything just use whitelists?
  3. Right now, V1 can't tell a real card from a clone with a matching UID — it has no way to know the difference. If you were designing this system for a real building, what's the very next question you'd need to answer to fix that, even if you can't fix it yet?
  4. Your V1 will light up an LED the instant it sees a matching UID, with zero other checks. What's one everyday security system you interact with that also makes a decision that fast, and does its speed ever worry you?

Directions

  1. Wire a single LED as your access indicator.
  2. Hardcode one scanned card's UID as an authorized whitelist entry.
  3. Write byte-by-byte comparison logic that lights the LED only on a match.
  4. Expand your whitelist to at least 2 authorized UIDs and test all cases.
  5. Submit your code and photo, and add your V1 photo to Page 2.5 on your Google Site.

Two-period lesson, first version of this unit's V1→V2→V3 sprint. You're knowingly building the exact vulnerability from 5.2 — a deliberate starting point, not a mistake.

Notes

Look up these definitions:

  • Whitelist
  • Blacklist
  • Byte comparison
  • Access log

Key idea: a whitelist only allows specifically listed items (everything else denied by default) — the more secure default approach, and what V1 uses. A UID is made of several bytes, so comparing means checking every byte matches (same idea as Lesson 4.4's String comparison, different data type). V1's scope is intentionally limited — no servo yet (V2), no LCD yet (V3) — and it carries the exact vulnerability from 5.2: a cloned card with a matching UID gets in, with no way for V1 to tell the difference. That's a deliberate starting point to improve from.
