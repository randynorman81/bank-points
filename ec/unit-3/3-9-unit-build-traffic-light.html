3.9 — Unit Build: Traffic Light (Real Hardware)

🔔 Bell Ringer — Think About It
  1. Your TinkerCAD traffic light in 2.9 only had to control three LEDs. Today's real version also has to read a real pedestrian button, the same way you practiced in 3.6. Why does adding one more real input make this build more than just "the same thing, but real"?
  2. You've now built the same core project twice — once simulated, once real. What's the single biggest difference between "it works in the simulator" and "it works in my hands," now that you've done both?
  3. A real embedded engineer never gets a lesson page walking them through their own project, and today you have even less scaffolding than 2.9 did. What's the first thing you'd actually try if you got stuck with no directions to fall back on?
  4. Your real traffic light works even though nobody is grading whether the timing is "realistic" down to the second. Why might building something that just works still not be good enough for a real engineer shipping a product?

Notes

No new vocabulary today.

What you're building: a working real traffic light using red, yellow, and green LEDs on a real breadboard, combining everything from this unit — real digital output (3.3), variables (3.4), a real button input (3.6), timing/sequencing (3.6), and safe circuit wiring verified with a multimeter (3.7). New for this build: add the pedestrian-crossing button from 3.6 so the sequence responds to a real request at a safe point in the cycle. Requirements: all three LEDs wired correctly with resistors; the pedestrian button integrated and working; realistic, differentiated timing; at least one variable; every line commented; a fully working, debugged final circuit. Not a day to ask AI to generate your code — using it to understand a specific error is fine, having it write your solution defeats the point.
