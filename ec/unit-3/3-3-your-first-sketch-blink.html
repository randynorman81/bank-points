3.3 — Your First Sketch: Blink (Real Hardware)

🔔 Bell Ringer — Think About It
  1. Adding a second LED that blinks opposite your first one (on while the other is off) sounds like double the work, but it's really the same idea twice. What's the one core concept from Blink that makes this addition straightforward instead of starting over?
  2. In TinkerCAD, uploading code and seeing the result happens instantly. On real hardware, there's an actual multi-second delay while your code compiles and uploads over USB. Why might that small real delay actually change how you debug, compared to the simulator?
  3. A loose breadboard wire can cause a real LED to flicker unpredictably — something that never happens in a simulated circuit. Why do you think physical connections are one of the most common real debugging problems, even for experienced engineers?
  4. Your two LEDs alternate: when one is HIGH, the other is LOW. What's the simplest way to write that in code so you're not just duplicating every line twice?

Notes

Look up these definitions:

  • Sketch
  • setup()
  • loop()
  • digitalWrite()
  • Alternating output

Key idea: same two required functions as always — setup() runs once, loop() runs forever after. Today, wire your Blink circuit for real on a breadboard, then add a second LED on its own pin and resistor that blinks the opposite of the first: while LED 1 is HIGH, LED 2 is LOW, and they swap together. You don't need new commands to do this — just two digitalWrite() calls per LED, using the opposite state each time. Common first-upload problems on real hardware: wrong board or port selected in the IDE, missing semicolons/unmatched braces, an LED wired backwards, or a loose breadboard connection — none of which TinkerCAD ever makes you deal with.
