3.5 — PWM: Controlling Brightness (Real Hardware)

🔔 Bell Ringer — Think About It
  1. In 3.4, turning a potentiometer changed timing (milliseconds). Today it'll change brightness (a PWM value). Same physical action, two completely different effects on your program — why does that make sense given what each value is used for?
  2. Real PWM brightness and simulated PWM brightness are supposed to look identical to your eyes. If you compare your real LED fading to your TinkerCAD version side by side, what's actually different, if anything?
  3. map() has to convert a 0–1023 potentiometer reading into a 0–255 PWM value. Why couldn't you just use the potentiometer's raw 0–1023 reading directly in analogWrite()?
  4. If you turn the potentiometer all the way and the LED doesn't reach full brightness, what are two different things — one about wiring, one about code — that could cause that?

Notes

Look up these definitions:

  • PWM (Pulse Width Modulation)
  • analogWrite()
  • Duty cycle

Key idea: same PWM concept as 2.5 — a pin is still only ever fully on or fully off, switching fast enough to look like a smooth brightness level. Instead of a pre-scripted fade, wire a real potentiometer to an analog pin and use map(analogRead(pin), 0, 1023, 0, 255) to convert its reading directly into a value for analogWrite(). Now brightness responds instantly to a physical knob instead of following a timed loop — the same map() pattern from 3.4, applied to a different real-world output.
